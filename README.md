# vitest-mock-is-too-slow

A synthetic but realistically shaped frontend test suite showing that **module mocks (`vi.mock`)
make Vitest's browser mode much slower**, while the exact same tests with the exact same mocks cost
next to nothing under Rstest's browser mode, and under every runner once no real browser is
involved.

It was extracted from a real application whose browser-mode suite (a few hundred test files) became
painfully slow: files that used `vi.mock` spent ~10× longer importing than files that did not. The
fixture reproduces that shape: a design system of 9 packages behind barrels, a shared layer, an app
shell (context + router) that most tests mock, test utilities that mount through the app shell, and
50 feature folders.

```sh
nix develop    # the pinned toolchain: Node, pnpm, Bun, uf and Chromium (flake.nix / flake.lock)
pnpm install
pnpm bench
```

`pnpm bench` generates the fixture if needed and runs every runner on both suites, then prints the
tables below. Without Nix it uses Node (≥ 24), pnpm and Bun from `PATH`, lets Playwright download
its Chromium and downloads uf; that works, but nothing is pinned. See [Running it](#running-it).

## What is compared

Two suites, generated by [`scripts/generate.ts`](scripts/generate.ts):

| Suite                   |                                                                 |
| ----------------------- | --------------------------------------------------------------- |
| `fixture/tests/nomock/` | 500 test files × 10 tests = 5,000 tests                         |
| `fixture/tests/mock/`   | the same 500 files plus 3–5 module mocks each (~1,900 in total) |

Per test file in the mock suite (the mix of the original app):

- `#src/app/context` and `#src/app/router`: replaced with a factory (every file),
- the feature's own `api` module: replaced with a factory (every file),
- a design-system component module wrapped in spies with `{ spy: true }` (half / a quarter of the files).

The only other difference between the suites is the last test of each file, which asserts which app
context it got (`"Test User"` from the mock, `"Guest"` from the real module). This proves that every
runner actually applies the mocks.

Runners and environments:

| Runner            | Real browser (Playwright's headless Chromium)      | happy-dom                            | `isolate`                                           |
| ----------------- | -------------------------------------------------- | ------------------------------------ | --------------------------------------------------- |
| Vitest            | browser mode, `@vitest/browser-playwright`         | `environment: "happy-dom"`           | `true` / `false`                                    |
| Vite+ (`vp test`) | the same, through Vite+'s own Vitest and Vite core | the same                             | `true` / `false`                                    |
| Rstest            | browser mode, `@rstest/browser`                    | `testEnvironment: "happy-dom"`       | `true` / `false`                                    |
| `bun test`        | no browser mode                                    | happy-dom registered in a preload    | `--parallel` / `--parallel --no-isolate`            |
| `uf test`         | `--browser` cannot mock modules                    | happy-dom registered in a setup file | always (the module registry is reset between files) |

Every runner gets the same number of parallel workers (`--workers`, default `min(12, CPUs − 1)`,
which is Vitest's and Rstest's own browser-mode default). The happy-dom table puts all five runners
on equal footing; the browser table compares the three that have a browser mode, on the same
Chromium.

### Are the conditions equal?

- **The same Chromium.** Vitest, Vite+ and Rstest all start it through Playwright's
  `chromium.launch({ headless: true })`. Inside `nix develop` the only Chromium there is is the
  Nix-built headless shell, and every run records the executable Playwright launched (the line
  under the browser table).
- **The same parallelism.** Every runner gets `--workers` workers.
- **The same tests and mocks**, through `#host` (below).
- **Isolation is not lighter for Rstest.** With `isolate: true`, Vitest keeps one page per worker
  and gives every test file a fresh iframe; Rstest gives every test file a new browser context and
  page.
- **What differs is the architecture.** Vitest serves a test file's module graph unbundled from
  the Vite dev server, so every isolated test file requests each of its modules again (a few
  hundred here); Rstest serves one bundle per test file. That is why Vitest's no-mock run already
  costs more Chromium CPU. The `isolate: false` rows, where modules load once per worker, take that
  difference out. The "mocks cost" column compares each runner with itself and does not depend on
  it.

### One test source for every runner: `#host`

Test files never import a runner. They import `#host` and use `host.mock()` / `host.fn()`:

```ts
import { afterEach, describe, expect, host, it } from "#host";
import { createListView } from "#src/features/feature-00/components/list-view";

host.mock("#src/app/context", () => ({ useAppContext: () => ({/* … */}) /* … */ }));
host.mock("#src/ui/overlay/tooltip", { spy: true });
```

[`host/types.ts`](host/types.ts) is the API as test files see it. Each runner supplies it its own
way, from its own directory under [`host/`](host):

| Runner        | How `#host` reaches it                                      | Files                                                            |
| ------------- | ----------------------------------------------------------- | ---------------------------------------------------------------- |
| Vitest, Vite+ | compile time: `"#host"` → `"vitest"`, `host.` → `vi.`       | `host/vitest/plugin.ts` (Vite plugin)                            |
| Rstest        | compile time: `"#host"` → `"@rstest/core"`, `host.` → `rs.` | `host/rstest/plugin.ts` (Rsbuild plugin)                         |
| Bun           | run time: the `"bun"` condition of `"#host"`                | `host/bun/host.ts`, `host/bun/setup.ts` (preload: happy-dom)     |
| uf            | run time: the `"repro-uf"` condition of `"#host"`           | `host/uf/host.ts`, `host/uf/setup.ts` (happy-dom, mock hoisting) |

Why the differences:

- Vitest only hoists `vi.mock()` and Rstest only hoists `rs.mock()`: both match the literal
  identifier. So for them `#host` is a macro, and what they execute is exactly a hand-written test
  for that runner ([`host/rewrite.ts`](host/rewrite.ts)).
- Bun's `mock.module()` is not hoisted but replaces a module's exports in place, even for files
  that imported it already, so a runtime object is enough.
- uf's `uft.mock()` is not hoisted and only affects imports that start after it. `host/uf/setup.ts`
  therefore hoists the mocks the way Vitest does: the mocks run first, then every static import
  becomes an `await import()`, one after another.

Only forms every runner supports with the same meaning are used: synchronous factories and
`{ spy: true }`. Source modules are addressed through package.json subpath imports (`#src/*` →
`./fixture/src/*.ts`, relative imports with explicit `.ts`), so no runner needs alias configuration
and Node can load everything as is.

## Why `vi.mock` is slow in browser mode

Found with the patches in [`patches/`](patches) and V8 CPU profiles; the profile table above shows
the numbers for the current versions.

1. **Every `vi.mock()` installs a Playwright route for the whole browser context.**
   `@vitest/browser-playwright` registers one `page.context().route(predicate, handler)` per mocked
   module and removes it again when the file is done. As soon as a context has a route, Playwright
   intercepts **every** request of that context: Chromium pauses it (`Fetch.requestPaused`), Node
   evaluates every registered predicate, and tells Chromium to continue. Each module request of a
   mocked test file becomes a CDP round trip through the Node main thread.
2. **Routes switch off the browser's HTTP cache.** While request interception is on, Playwright
   sends `Network.setCacheDisabled({ cacheDisabled: true })`. Without mocks, repeated module
   requests are revalidated with `If-None-Match` and answered with `304`; with a mock in the file,
   every module is transferred in full (`200`) again, for every test file.
3. **Hoisted imports run one after another.** To run mocks before imports, `@vitest/mocker`
   rewrites every static import of the test file into its own
   `const __vi_import_N__ = await import(…)`, so the module graph of a mocked file loads as a
   waterfall instead of in parallel.
4. **All of this lands on one thread.** The Vite dev server, the Vitest RPC and the Playwright
   client and server all live on the Node main thread. Its event loop is saturated during the run,
   so the extra per-request work turns directly into wall-clock time, and gets worse the busier the
   machine is.

Rstest's browser mode bundles the test files and implements `rs.mock` in the bundler's module
runtime: no request interception, no cache bypass, no import waterfall. Without a browser, 1 and 2
do not exist and 4 is much lighter, and the waterfall of 3 is cheap because an import is an
in-process call rather than a request; compare the happy-dom table.

## Running it

```sh
pnpm bench                       # everything, 1 round
pnpm bench --repeat 3            # 3 rounds, median
pnpm bench --runners vitest,rstest --envs browser --suites mock --isolate true
pnpm bench --workers 4           # parallel workers per runner
pnpm bench --experiments         # + Vitest with the experimental patches below
pnpm bench --profile --cpu-prof  # + per-file request stats, route stats, event loop, CPU profile
pnpm generate --features 20      # a smaller fixture (default: 50 features × 10 files × 10 tests)
```

Results are written to `results/<--out>/` (`summary.md`, `runs.json`, one log per run). The runner
commands themselves are plain:

```sh
pnpm test:vitest fixture/tests/mock/
pnpm test:vp fixture/tests/mock/
pnpm test:rstest fixture/tests/mock/
pnpm test:bun                    # bun test --parallel ./fixture/tests/
pnpm test:uf                     # uf test fixture/tests/
REPRO_ENV=happy-dom REPRO_ISOLATE=false pnpm test:vitest fixture/tests/mock/
```

Vitest's browser mode is bound by the Node main thread, so benchmark on an idle machine;
`pnpm bench` warns when the load average is high.

## Profiling patches

[`patches/`](patches) holds `pnpm patch` patches. They are always installed but do nothing unless
their environment variable is set.

| Patch                        | Variable                       | What it does                                                                                                                                                                                                  |
| ---------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@vitest/browser`            | `REPRO_PROF_DIR`               | the tester reports, per test file, the Resource Timing of its import (requests, waterfall time); the server records what it answered (`200` / `304`) and samples the Node event loop utilization every second |
| `@vitest/browser-playwright` | `REPRO_PROF_DIR`               | counts route registrations, predicate evaluations and the time spent in `route` / `unroute`                                                                                                                   |
| `@vitest/mocker`             | `REPRO_EXP_PARALLEL_IMPORTS=1` | experiment: start all hoisted imports first and `await Promise.all(…)` them, instead of one `await import()` after another                                                                                    |
| `playwright-core`            | `REPRO_EXP_KEEP_CACHE=1`       | experiment: keep the HTTP cache enabled while request interception is on                                                                                                                                      |

[`scripts/profile.ts`](scripts/profile.ts) and [`scripts/cpuprofile.ts`](scripts/cpuprofile.ts)
summarise what they write.

## Layout

```
flake.nix            the pinned toolchain (nix develop)
host/                "#host": types.ts, rewrite.ts, and one directory per runner
scripts/
  generate.ts        fixture generator (deterministic)
  bench.ts           runs the matrix, measures wall clock and CPU, writes results/
  profile.ts         summarises the profiling patches' output
  cpuprofile.ts      summarises V8 CPU profiles by package
  uf.ts              runs uf (outside Nix: downloads the pinned release and checks its SHA-256)
patches/             pnpm patches (profiling + experiments)
vitest.config.ts     Vitest
vite.config.ts       Vite+ (`vp test`)
rstest.config.ts     Rstest
bunfig.toml          Bun
```

Scripts are plain TypeScript run by Node's built-in type stripping.

## Notes

- `playwright` is pinned to the version of nixpkgs' `playwright-driver`, so that Playwright uses the
  Chromium built by Nix (`PLAYWRIGHT_BROWSERS_PATH`) and downloads nothing.
- `vp test` runs Vite+'s own Vitest on Vite+'s own Vite core. The Playwright provider package
  (`@vitest/browser-playwright`, a peer of Vite+) is the same 5.0.3 install the standalone Vitest
  uses; pnpm binds its peers to the standalone `vite` / `vitest` because both are installed here.
- `uf test` honours `.gitignore` when it discovers test files, and `fixture/` is ignored, so it is
  always given `fixture/tests/` explicitly.
